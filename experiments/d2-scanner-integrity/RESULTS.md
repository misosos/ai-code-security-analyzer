사전 등록 기준에 따른 판정: **`EVIDENCE_INSUFFICIENT`** ([프로토콜](PROTOCOL.md) 8절)

판정이 `EXISTING_TOOLS_SUFFICIENT`가 아닌 이유는 최소 스크립트(Arm C)가 고정 라벨 기준으로 2건을 놓쳤기 때문이다. 그 2건은 제가 만든 사례가 의도한 실패 상황을 실제로 만들지 못한 것으로 보이지만, 라벨을 사후에 바꾸지 않는다. 판정이 `SCANNER_INTEGRITY_VALUE_SUPPORTED`가 아닌 이유는 명확하다. 현재 제품은 어떤 모드에서도 스크립트보다 낫지 않았다.

## 4. 관찰된 사실

### Semgrep 기본 실행

- 13개 불완전 사례 중 11개에서 종료 코드 0이었다. 그중 7개는 Finding 0건이었다.
- stderr 요약은 이 11개 모두에서 `✅ Scan completed successfully.`로 시작했다. **검사한 파일이 0개인 I1도 같다.**
- 타임아웃(Gt)은 종료 코드 0이고, 기본 요약에 타임아웃이 언급되지 않으며 `Parsed lines: ~100.0%`로 나온다. JSON `errors`에는 `Timeout`이 있다.
- 미추적 gitignore 파일(D)은 `--verbose` JSON의 `scanned`와 `skipped` 어디에도 나오지 않는다. 요약에는 모든 사례에 공통으로 붙는 `Scan was limited to files tracked by git` 한 줄뿐이다.

### 사람이 읽는 기본 요약 (사후 정성 관찰, 채점 제외)

| 사례 | 기본 요약에 불완전 신호가 있는가 |
| --- | --- |
| Bs | 있음: `Files larger than files 1.0 MB: 1` |
| C, Cd | 있음: `Files matching .semgrepignore patterns: 1` |
| B | 약함: `Parsed lines: ~86.7%` |
| Gt, D, F2, I1 | 없음 (I1은 `Targets scanned: 0`이 보이지만 성공 표시와 함께 나옴) |
| Hn (완전) | `.semgrepignore patterns: 1`이 똑같이 표시됨. 의도한 제외와 의도하지 않은 제외가 구분되지 않음 |

### `--strict`

기본 실행 대비 B(종료 3)와 Gt(종료 2)만 추가로 잡았다. 크기 제한, ignore, 규칙 누락, 잘못된 대상 디렉터리는 그대로 통과했다. 정상 검사를 막은 사례는 없었다.

### 최소 스크립트 (152줄, 표준 라이브러리)

- 유효하게 구성된 불완전 사례 11개를 모두 잡았고, 원인 분류가 모두 라벨과 일치했다. 완전한 검사 5개는 모두 통과시켰다.
- D와 F2는 스크립트만 잡았다. 각각 "디스크에 있는데 scanned 목록에 없는 소스 파일"과 "규칙 파일 해시가 기대값과 다름"으로 잡았다. 둘 다 Semgrep 출력만으로는 알 수 없고 **선언된 의도**가 있어야 한다.

### 현재 제품

- 제품이 차단한 사례는 예외 없이 스크립트도 차단했다. 제품만 잡은 불완전 사례는 없다.
- CLI와 API 경로는 비-verbose로 실행하므로 범위 제외(Bs, C, Cd, J)를 `completed`로 보고했다.
- 조사 모드는 범위 제외를 잡지만 사유가 `evidence_unavailable` 하나로 뭉개지고, 선언된 제외인 `node_modules/`도 차단한다(Hn).
- 세 모드 모두 Finding 5,000건을 처리하지 못했다(`output_limit_exceeded`, Finding 0건 반환).
- 제품이 스크립트보다 잘한 사례는 없다. D1에서 관찰한 "부분 파싱을 `partial`로 표시"는 이번에도 확인됐지만(B), 스크립트의 `errors` 검사가 같은 것을 원인 분류와 함께 잡는다.

## 5. 모든 Arm이 놓친 2건 (A, F1)

고정 라벨 기준으로는 두 사례 모두 "불완전"이며 여섯 Arm 전부가 통과시켰다. 원시 결과를 보면 Semgrep이 불완전 신호를 전혀 내지 않았다.

| 사례 | Semgrep 출력 | 해석 |
| --- | --- | --- |
| A | `errors` 비어 있음, `Parsed lines: ~100.0%`, skipped 없음 | 구문 오류가 있는 파일에 규칙이 요구하는 문자열이 없어 Semgrep이 그 파일을 파싱하지 않은 것으로 보인다 |
| F1 | `errors` 비어 있음, `Rules run: 3` | Semgrep이 패턴 `eval(`를 유효한 패턴으로 받아들였다. 규칙은 실행됐다 |

즉 제가 만든 사례가 의도한 실패 상황을 만들지 못했을 가능성이 높다. 라벨은 "구문 오류가 있다", "패턴이 파싱되지 않는다"는 제 가정에서 나왔고, 그 가정이 Semgrep의 실제 동작과 달랐다.

**사후 탐색 (채점 이후 수행, 평가에 포함하지 않음)** — `exploratory/posthoc-output.txt`

- A와 같은 파일에 주석으로 `eval`이라는 단어만 추가하면 `PartialParsing` 오류가 나타났다. "규칙과 무관한 파일은 파싱하지 않는다"는 해석과 일치한다.
- 실제로 파싱되지 않는 패턴(`$X ==== $Y` 등)을 넣으면 `errors`에 `Rule parse error`(level `error`)가 나온다. **이때도 기본 종료 코드는 0이다.** 스크립트의 규칙 2는 이 오류를 잡는 형태다.

이 탐색은 사전 등록 밖이므로 판정을 바꾸는 근거로 쓰지 않는다. 다만 "스크립트가 충분한가"에 대해 이번 실험이 답하지 못한 부분이 이 2건이라는 점은 분명하다.

**민감도**: A와 F1을 구성 실패로 보고 제외하면 스크립트는 M1 = 0, M2 = 0이 되어 `EXISTING_TOOLS_SUFFICIENT` 기준을 충족한다. 포함하든 제외하든 제품이 스크립트보다 낫지 않다는 결과는 같다.

## 6. 프로토콜 이탈

- 사전 등록 파일 3개는 커밋 이후 변경하지 않았다. `integrity_check.py`, `run_case.py`, `evaluate.py`는 전체 실행 결과를 본 뒤 수정하지 않았다.
- 전체 실행 전에 사례 Hp를 한 번 스모크 테스트했다(결과는 `raw/`에 포함하지 않음). 그 직전에 오류 분류 함수를 프로토콜 문구의 순서와 정확히 맞게 고쳤다. 어떤 사례 결과도 보기 전이다.
- **원시 결과 사후 정제**: 실행기가 치환하지 못한 임시 경로 조각이 24개 파일에 남아 있었다(verbose 로그의 줄바꿈, 120자 절단). 저장 후 해당 경로 문자열만 `<TMP-TRUNCATED>`로 치환했다. 판정과 채점 결과는 치환 전후 동일하다.

## 9. 결정

**1. 이 문제는 실제로 존재하는가?**
도구 동작 수준에서는 존재한다. 기본 실행은 불완전한 검사 13개 중 11개를 종료 코드 0과 "성공" 표시로 끝냈다. 실제 업무에서의 빈도와 피해는 가설이다.

**2. 기존 도구가 이미 해결하는가?**
옵션만으로는 아니다. `--strict`는 9건을 통과시켰다. verbose JSON과 152줄 스크립트는 유효한 불완전 사례 11개를 모두 잡았다. 다만 스크립트의 충분성은 사전 등록 기준(M1 = 0)을 충족하지 못했으므로 이 실험으로 확정되지 않았다.

**3. 현재 프로젝트에 추가 가치가 있는가?**
없다. 제품이 잡은 것은 스크립트가 전부 잡았고, 제품은 모드에 따라 4~8건을 놓쳤으며(스크립트는 2건), 정상 검사를 1~2건 차단했다.

**4. 최소한의 개선으로 해결 가능한가?**
그렇다. 필요한 것은 CI에 넣는 스크립트 하나와 "무엇을 검사해야 하는가"를 적은 선언(제외 목록, 규칙 해시)이다. 핵심은 도구가 아니라 선언된 의도다.

**5. 제품 개발에 투자할 근거가 있는가?**
없다.

**6. 어느 방향을 중단할 것인가?**
스캐너 무결성을 제품 차별점으로 삼는 방향, 그리고 조사 모드의 `partial` 판정을 확장하는 작업. D1과 합치면 이전 감사에서 남겨 둔 차별성 후보(소실 조사, 비교 가능성, 그 결합)는 모두 근거를 얻지 못했다.

## 10. "기존 도구로 충분하다면 왜 이 프로젝트를 더 개발해야 하는가?"

제품으로서 설득할 근거는 D1과 D2 어디에서도 나오지 않았다. 두 실험 모두에서 작은 스크립트가 제품과 같거나 더 나았다. 따라서 새 기능 구현을 제안하지 않는다.

남는 이유는 제품 가치가 아닌 것들이다.
- 학습과 포트폴리오: Semgrep을 안전하게 감싸는 방법, 실패 상태를 다루는 방법, 그리고 자신의 가설을 사전 등록 실험으로 기각한 기록.
- D1과 D2의 스크립트와 결과 자체는 재사용 가능한 산출물이다. 공개 여부는 별도 결정 사항이다.

## 11. 한계

1. 같은 연구자가 사례, 라벨, 스크립트 규칙을 같은 세션에서 설계했다. 독립 검증이 아니다.
2. 사례 2개(A, F1)는 의도한 상황을 만들지 못했다. 사례 설계 단계에서 Semgrep 동작을 사전에 확인하지 않은 결과다.
3. 스크립트만 "선언된 의도"를 입력으로 받는다. 제품에는 이를 전달할 방법이 없으므로 D와 F2는 제품이 구조적으로 잡을 수 없는 사례다. 이 비대칭은 사전에 명시했다.
4. 합성 18개 사례다. 실제 저장소 규모, 모노레포, 다른 언어, 다른 Semgrep 버전은 시험하지 않았다.
5. 스크립트가 틀릴 수 있는 지점을 시험하지 않았다: verbose 목록이 매우 긴 저장소, 생성 코드가 많은 저장소에서의 오탐, JSON 스키마 변경.
6. HTTP 계층과 대시보드는 실행하지 않았다.

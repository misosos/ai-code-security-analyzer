판정: **`BASELINE_SUFFICIENT`** ([사전 등록 프로토콜](PROTOCOL.md) 10절 기준)

## 4. 잘못된 판단 사례

### Arm A와 Arm C가 공통으로 틀린 4건 (원인: 위치 기반 동일성)

- **B, C**: 코드가 바이트 단위로 같은데 "기존 Finding 소실 + 신규 Finding 1건"으로 보고했다.
- **Da**: 동일한 위험 줄 2개 중 첫째를 지우자 둘째가 4행으로 올라왔다. 두 Arm은 **지워진 첫째를 "유지"로, 남아 있는 둘째를 "소실"로** 보고했다. 가짜 신규 Finding도 없어서 겉보기에는 "1건 해결"로 깔끔하게 보인다. 건수는 맞지만 어느 것이 남았는지가 뒤바뀐다.

### Arm C에만 있는 한계

- **A와 J를 구분할 정보가 없다**: 실제 제거와 탐지 회피 모두 `UNDETERMINED`, 원인 없음. Arm B도 둘을 같은 `CODE_CHANGED_AT_MATCH`로 분류하지만, 최소한 "매치 줄이 바뀌었다"는 사실과 범위·규칙이 동일하다는 사실을 준다.
- **F**: 경로가 보고되지 않아 원인 없음.
- **Ka, Kb**: 제외는 관찰했으나 코드 변경은 보지 못했다.
- **Ib**: 평가는 `INCOMPARABLE` + `scan_incomplete`였으나 Finding 2건을 `baselineOnly`로 나열했다. 사전 등록 정규화 표에 따라 "소실, 원인 없음"으로 채점했다(6절 민감도 참조).
- **E, Ka, Kb, Ia**: 조사 모드의 전체 판정은 모두 `INCOMPARABLE`이었다. `.semgrepignore`가 있거나 구문 오류가 있으면 검사가 `partial`이 되기 때문이다.

### Arm B의 약점 (이번 채점에서는 틀리지 않음)

- **Ia**: Semgrep은 종료 코드 0을 반환했고 `errors`에 `PartialParsing`을, `paths.skipped`에 `analysis_failed_parser_or_internal_error`를 남겼다. Arm B는 Finding이 유지됐다고 옳게 판정했지만 부분 파싱 사실을 경고로 올리지 않는다. 제품은 같은 검사를 `partial`로 표시했다. 이 점은 제품이 스크립트보다 나은 유일한 관찰이다.
- **J**: `CODE_CHANGED_AT_MATCH`는 수정의 증거가 아니다. A와 J는 Semgrep과 Git 수준에서 구분할 수 없으며 사람의 코드 검토나 다른 탐지 수단이 필요하다.

## 5. `semgrep --baseline-commit` 검토

14개 사례 모두에서 결과 0건을 반환했다(Ib는 종료 코드 7).

- **할 수 있는 것**: "기준 커밋 대비 새로 생긴 Finding"만 보여 준다. 줄 이동(B)과 이름 변경(C)에서 가짜 신규 Finding을 내지 않았다. 위치 기반 비교보다 낫다.
- **할 수 없는 것**: 사라진 Finding은 출력하지 않는다. 소실 조사에는 정보를 주지 않는다. 규칙 파일이 Git 저장소 밖에 있으면 두 커밋에 같은 현재 규칙을 적용하므로 규칙 변경도 드러나지 않는다.

## 6. 프로토콜 이탈과 민감도

- **이탈 없음**: `PROTOCOL.md`, `labels.json`, `build_cases.py`는 사전 등록 커밋 이후 변경하지 않았다. `baseline_b.py`와 `evaluate.py`는 전체 실행 결과를 본 뒤 수정하지 않았다.
- **공개**: 전체 실행 전에 사례 B를 한 번 스모크 테스트했다(결과는 `raw/`에 포함하지 않음). 그 뒤 스크립트를 바꾸지 않았다.
- **민감도 (Ib)**: 제품의 `INCOMPARABLE` + `scan_incomplete`를 `SCAN_INCOMPLETE` 원인으로 인정하도록 규칙을 바꾸면 Ib 2건은 EXACT가 된다. 같은 규칙은 E, Ka, Kb에 라벨에 없는 SCAN 원인을 추가한다. 어느 쪽으로도 최종 판정은 바뀌지 않으며, 사전 등록 채점을 그대로 유지한다.

## 8. 차별성 판단

**Q1. 기존 도구로 충분히 해결되는 문제는?**
이번 14개 사례 전부. 줄 이동, 이름 변경, 동일 코드 중복, 파일 삭제, `.semgrepignore`, `.gitignore`, 규칙 제거, 규칙 변경, 검사 실패, 복수 원인을 227줄짜리 표준 라이브러리 스크립트가 구분했다.

**Q2. 기존 도구만으로 판단하기 어려운 문제는?**
- 실제 수정과 탐지 회피의 구분(A 대 J). 스크립트도 제품도 못 한다.
- 스크립트의 전제 조건 유지. 기준 시점의 verbose JSON, 종료 코드, 규칙 파일 사본, 커밋 ID가 **그때 저장돼 있어야** 한다. 이것은 분석 문제가 아니라 운영 규율 문제다.

**Q3. 우리 프로젝트가 이미 해결하는 문제는?**
- 부분 파싱을 `partial`로 표시(Ia). 스크립트는 경고하지 않았다.
- `.semgrepignore` 제외 관찰(E). 스크립트도 동일하게 한다.
그 외에는 없다.

**Q4. 새로운 제품 기능이 필요한 문제는?**
이 실험에서는 확인되지 않았다.

**Q5. 구현해도 스크립트보다 나아질 근거가 있는가?**
없다. 제품이 스크립트 수준에 도달하려면 Git 연동과 내용 기반 동일성을 새로 만들어야 하고, 그 결과물은 이 스크립트와 같은 일을 한다.

**Q6. 필요한 기능이 스크립트 하나라면 독립 제품이 합리적인가?**
합리적이지 않다. 스크립트 하나와 "검사 때마다 무엇을 저장할지"를 적은 짧은 절차서가 더 적합하다.

## 9. 가장 강력한 반론과 이 실험의 한계

1. **같은 사람이 사례와 스크립트를 같은 세션에서 설계했다.** 사례는 스크립트 규칙이 예상하는 원인 범주와 일치한다. 30/30은 "예상한 범주를 구현대로 처리했다"는 뜻이며 독립 검증이 아니다.
2. **적대적 사례가 없다.** 다음은 시험하지 않았다: 다른 파일로 잘라 붙여 넣은 코드, 이름 변경과 대폭 수정이 겹쳐 `git diff -M`이 이름 변경으로 인식하지 못하는 경우, 여러 줄에 걸친 매치, 포매터가 매치 줄을 다시 쓴 경우, 수백 개 Finding, 모노레포, taint 규칙의 source·sink가 다른 파일에 있는 경우.
3. **F의 판정은 추론이다.** "디스크에 있는데 scanned 목록에 없다"로 제외를 추정했다. Semgrep이 사유를 보고한 것이 아니다.
4. **규칙 비교가 텍스트 기반이다.** 주석만 바뀌어도 `RULE_CHANGED`가 된다. 여러 파일에 걸친 규칙 구성이나 레지스트리 규칙은 다루지 않는다.
5. **사람을 측정하지 않았다.** 스크립트 출력을 사람이 올바르게 읽는지, 시간이 줄어드는지는 모른다.
6. **이 결과는 "제품이 필요 없다"의 증명이 아니다.** "이 14개 사례에서 제품이 필요하다는 증거가 나오지 않았다"이다.

## 10. 사용자 검증이 필요한 가설

- 실무에서 기준 시점의 검사 산출물이 실제로 보존되는가. 보존되지 않는다면 필요한 것은 분석 도구가 아니라 보존 절차다.
- Finding 소실 조사가 실제로 반복되는 업무인가, 드문 예외인가.
- Semgrep AppSec Platform을 쓰지 않는 조직이 스크립트 유지보수를 감당하는가.

## 11. 다음 개발 방향

1. 소실 조사를 제품 차별점으로 삼는 방향(이전 감사의 후보 A, C, E)은 **중단**한다. 이전 감사에서 사전에 정한 포기 조건(기준선 정확도 90% 이상, 잘못된 수정 판정 0건)이 충족됐다.
2. v2 조사 API, 메모리 레지스트리, 평가기에 대한 추가 투자를 중단한다.
3. 이 스크립트와 절차를 문서로 공개할 가치가 있는지는 별도 결정 사항이다.
4. 제품을 계속한다면 범위를 "Semgrep을 안전하게 감싸는 학습용 포트폴리오"로 고정한다.
5. 방향을 다시 열려면 9절 2번의 적대적 사례를 **다른 사람이 설계한** 세트로 스크립트를 깨뜨리는 실험이 먼저 필요하다.

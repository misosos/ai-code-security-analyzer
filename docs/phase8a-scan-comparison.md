# Phase 8A — 검사 결과 비교

## 목적과 사용자 흐름

검사 결과 화면에서 사용자가 정상 완료된 결과를 직접 비교 기준으로 지정하고, 같은 대상과 규칙 프로필로 다시 검사한 뒤 두 응답에 관찰된 Finding ID 차이를 확인합니다. 기준 지정은 자동으로 이루어지지 않습니다. 비교 기준과 현재 결과는 React 메모리에만 존재하며 새로고침하거나 결과를 지우면 사라집니다. 토큰도 기존처럼 메모리에서만 보관됩니다.

1. 검사를 정상 완료합니다.
2. 결과 화면에서 **비교 기준으로 지정**을 누릅니다.
3. 같은 대상과 규칙 프로필로 다시 검사합니다.
4. 결과 화면의 **검사 결과 비교**를 펼쳐 범주별 항목과 기존 근거를 검토합니다.

## 비교 조건과 알고리즘

두 응답 모두 `scan_status=completed`, `completed=true`, `omitted_finding_count=0`이어야 합니다. 응답 문맥 상태와 검사 상태가 일치하고 Finding 수 요약이 내부적으로 일관되어야 합니다. 검사 대상 ID, 규칙 프로필 ID, Experimental 상태가 같아야 하며 양쪽 Semgrep 버전이 존재하고 동일해야 합니다. 동일 응답을 자기 자신과 비교하는 것도 차단합니다.

비교는 `finding_id`의 정확한 문자열 일치만 사용합니다.

- 이번 검사에서만 관찰: 현재 Finding ID에만 존재
- 양쪽에서 관찰: 두 Finding ID에 모두 존재
- 기준 검사에서만 관찰: 기준 Finding ID에만 존재

위치는 Finding ID 생성에 포함됩니다. 따라서 파일 또는 줄 이동은 같은 이슈라도 단독 관찰로 분류될 수 있습니다. 코드 내용의 동일성이나 취약점의 신규 발생·해결을 증명하지 않으며, 유사 항목을 추론해 병합하지 않습니다.

## 차단 동작

부분 검사, 실패·미완료 검사, 생략된 Finding, 서로 다른 대상·규칙 프로필·Experimental 상태·Semgrep 버전, 불일치 응답 문맥, 중복 ID 또는 Finding 수 불일치가 있으면 분류 그룹을 반환하지 않고 구체적인 이유를 표시합니다. API 응답은 기존 `parseScan()` 검증을 통과한 `ScanResponse`만 사용하며, 최대 50건 제한으로 생략된 항목이 있으면 전체 비교를 차단합니다.

## 상태 보관과 비동기 요청

기준은 사용자가 버튼을 눌렀을 때 검증된 응답과 대상·규칙 표시 문맥, Experimental 상태, 브라우저 수신 시각을 함께 메모리에 저장합니다. 새 검사 시작 시 과거 현재 결과와 상세 선택을 지우며 기준은 보존합니다. 실패한 재검사 결과를 성공 결과로 재사용하지 않습니다. 지연된 이전 요청이 새 상태를 덮지 못하도록 요청 순번을 확인합니다. 결과 지우기는 기준과 현재 결과를 함께 삭제합니다. 토큰 처리와 API 계약은 바꾸지 않았습니다.

## 보안 및 표현 제한

- 비교 데이터는 브라우저 밖으로 전송하거나 브라우저 저장소에 쓰지 않습니다.
- API가 반환한 Finding만 React 텍스트 노드로 렌더링하며 동적 HTML을 만들지 않습니다.
- 소스 코드 원문이나 절대 경로를 새로 표시하지 않습니다. 기존 Finding 상세의 증거 계약을 재사용합니다.
- `verification_status`, `evidence_validation_status`, `supported_claims`, `restricted_claims` 의미를 바꾸지 않습니다.
- 화면 문구는 “관찰” 표현을 사용하며 취약점 수정·해결을 확정하지 않습니다.

## UI 동작 및 한계

비교 요약은 접힌 상태로 나타나 기존 Finding 목록을 불필요하게 아래로 밀지 않습니다. 열면 두 수신 시각, 대상·규칙 문맥, Semgrep 버전, 비교 한계, 세 범주와 선택 Finding의 기존 근거를 확인할 수 있습니다. 비교는 현재 검사 결과 화면에만 있으며 새 최상위 메뉴나 저장 이력을 만들지 않았습니다.

## 검증

- Frontend: `npm run typecheck`, 전체 Vitest 65건, `npm run build` 통과
- Chromium: 전체 브라우저 테스트 20건 통과. 비교 상호작용과 1920/1440/1024/768/390/320px 가로 넘침 검사 포함
- Python: CI와 동일한 `uv run --locked python -m pytest -q -rs` 실행 결과 542 passed, 28 skipped
- 합성 Semgrep E2E: `SEMGREP_REQUIRED=1 npm run test:e2e:real` 통과 (Semgrep 1.182.1)
- 비교 UI 스크린샷: `docs/assets/phase8a/comparison-1440.png`, `docs/assets/phase8a/comparison-390.png`

320px 결과 화면 검증에서 기존 심각도 분포가 11px 넘치는 문제를 확인해 360px 이하에서 두 열로 재배치했습니다. 비교 상세는 접힌 요약으로 시작해 기존 Finding 탐색 위치를 과도하게 밀지 않습니다. 스크린샷은 검토용 합성 Finding과 합성 브라우저 API 응답을 사용했으며 제품의 실제 검사 결과가 아닙니다.
